## 1. 为什么需要这条通道

| 事实 | 证据 |
|---|---|
| 服务器（阿里云香港 DC IP）B站下载解析返回 `HTTP Error 412` | 2026-10-20 命令行直测复现；同日同版本 yt-dlp 本地家宽正常 |
| WorkBuddy 云沙箱同样 412 | 2026-10-10 线上实测 |
| B站 AI 总结**不受影响** | 走独立 `x/v2/dm/view` 弹幕池接口，不经过 yt-dlp，也不经过 playurl |
| yt-dlp 生态没有 B站的"PO Token 等价物" | 社区解法只有 Cookie / 代理 |

**★ 根因修正（2026-10-20 02:34 实测）**：不是"整个 IP 被 B站 拉黑"。服务器上逐层探测的结果是
412 只落在**未签名的内容请求**（`/video/BV..` 页面 HTML、未签名 `x/web-interface/view`），
而 `spi` / `nav` / 签名 `view-wbi` / 签名 `playurl` **全部 200**，playurl 甚至直接给 1080P。

推论：yt-dlp 之所以在服务器上失败，是它**第一步抓视频页 HTML 就被 412 打断**，根本没走到取流环节；
自研通道跳过页面、直接调签名 API，就绕开了这一层。所以优先级要改写为：

```
自研通道（跳过被拦的页面，直接签名调 API）  >  yt-dlp（会先抓页面，被 412 打断）
```

出口 IP 不再是无条件前提——**在本服务器上接口层已经证明不需要换 IP**（媒体 CDN 分发能力见 §7.1 阶段 2 验证）。

⚠️ 但别过度乐观：这条结论建立在"风控只拦未签名内容请求"的现状上，B站 随时可能收紧；
通道必须始终保留 yt-dlp 回退，且上线后要实测。

### 1.1 自研 vs yt-dlp 的边界（防"能自研就自研"的滑坡）

docs/02 选 yt-dlp 的初衷是"1000+ 平台由社区维护，我们不承担平台适配风险"——
它的意思是**不为长尾平台写适配器**，不是"一个都不写"。所以需要一条明确的准入标准，
避免以后每遇一个平台就自研，最后把社区维护的收益全丢掉：

**三条同时满足，才允许新增自研通道**：

1. **yt-dlp 在该平台彻底失败**，且没有任何配置项可解（Cookie、player_client、代理、插件都试过）；
2. **该平台占实际使用量的显著份额**（个人站经验值：前 2~3 个平台，约占 80%+ 请求）；
3. **通道已被实测复现**（有服务器侧的探测数据，不是"理论上应该行"）。

不满足就等 yt-dlp 升级，或换出口 IP——**不要动代码**。

自研的真实代价（必须写进预期）：维护责任从社区转嫁到自己。B站的失效触发点是
WBI 重排表、`dm_img_*` 指纹算法、清晰度权限、CDN 防盗链策略；缓解办法是
**算法逐行照抄 yt-dlp 源码 + 注释标注来源与版本**，每次升级 yt-dlp 时 diff 一遍它的
`extractor/bilibili.py`，跟着改——这样维护量和"抄一次"差不多。

> 更"符合初衷"的第三条路：把它写成 **yt-dlp 的 extractor 插件**，复用它的格式选择、
> 下载、ffmpeg 合并、进度回调，系统里仍只有一条下载管线（代码量约 100~150 行）。
> 代价是先验证插件能在**库直调模式**下被加载、且能覆盖默认 BiliBiliIE 的优先级；
> 部署上也多一个插件目录。未验证，作为备选方案记录。

## 2. 方案总览（开闭原则）

新增一个通道文件，不动既有 yt-dlp 主流程；B站 URL 优先走自研，失败自动回退 yt-dlp：

```
analyze(url)
  ├─ is_douyin_url  → douyin.analyze()          （既有）
  ├─ is_bilibili_url → bilibili.analyze()        （新增，失败抛异常）
  │      └─ 失败 → 继续往下走 yt-dlp             （兜底，行为不变）
  └─ yt-dlp                                      （既有）

download(task)
  ├─ is_douyin_url  → _run_douyin_download()     （既有）
  ├─ _bilibili 标记 → _run_bilibili_download()   （新增，ffmpeg 合并双流）
  └─ _run_download()                             （既有）
```

**交付形态：两个文件**（与上一轮给用户的说法一致）

| 文件 | 改动 | 说明 |
|---|---|---|
| `backend/app/bilibili.py` | 新增（约 250 行） | 自研通道全部逻辑，对齐 `douyin.py` 的写法 |
| `backend/app/downloader.py` | 改 3 处 | `import`；`analyze()` 加分支；`start_download()` 加分支 + `_run_bilibili_download()` |

`main.py`、前端、数据库**都不需要改**。

## 3. 调用链（已实测跑通的顺序）

```
① GET  x/frontend/finger/spi                铸造 b_3/b_4 → buvid3/buvid4（可选，§5）
② GET  x/web-interface/view?bvid=..         标题/封面/时长/up主/aid/cid/pages（多 P）
   └─ 若这里 412 → 改走 x/web-interface/wbi/view（签名版，服务器实测可过）
③ GET  x/web-interface/nav                  取 wbi_img.img_url + sub_url（未登录 code=-101，但 data 有值）
④ 计算 mixin key（64 位重排表取前 32 位），缓存 30s
⑤ GET  x/player/wbi/playurl?<签名参数>       fnval=4048 + try_look=1 + dm_* 四个指纹参数
⑥ 解析 dash.video[] / dash.audio[] → 直链（下载时带 Referer）
⑦ ffmpeg 合并视频轨 + 音频轨 → mp4
```

> **不要抓 `/video/{bvid}` 页面 HTML**：DC IP 上这个页面直接 412（服务器实测），
> 而且通道根本不需要它——标题/封面从 `view` API 拿。抓页面只会在第一步就自杀。

### 3.1 WBI 签名（照抄 yt-dlp `bilibili.py`，已验证）

```python
MIXIN_KEY_ENC_TAB = [46,47,18,2,53,8,23,32,15,50,10,31,58,3,45,35,27,43,5,49,
                     33,9,42,19,29,28,14,39,12,38,41,13,37,48,7,16,24,55,40,
                     61,26,17,0,1,60,51,30,4,22,25,54,21,56,59,6,63,57,62,11,
                     36,20,34,44,52]   # 64 个下标，官方前端 getMixinKey() 同款

# 1) 取 key：两个 URL 各取文件名去扩展名，拼成 64 字符，按表重排后取前 32 位
lookup = "".join(u.rpartition("/")[2].partition(".")[0] for u in (img_url, sub_url))
mixin_key = "".join(lookup[i] for i in MIXIN_KEY_ENC_TAB)[:32]

# 2) 签名：加 wts → 值里过滤掉 !'()* → 按 key 排序 → urlencode → md5(query + mixin_key)
params["wts"] = round(time.time())
params = {k: "".join(c for c in str(v) if c not in "!'()*") for k, v in sorted(params.items())}
query = urllib.parse.urlencode(params)
params["w_rid"] = hashlib.md5((query + mixin_key).encode()).hexdigest()
```

- **key 不能硬编码**：每天轮换，必须实时取 `nav`。缓存 30s（yt-dlp 的保守值，官方确切过期时间不明）
- `nav` 未登录返回 `code: -101 账号未登录`，但 `data.wbi_img` 是有效的——**不要按 code 判断直接报错**

### 3.2 playurl 参数（★ 本节是全文最重要的一页）

```
GET https://api.bilibili.com/x/player/wbi/playurl
  bvid=BV..          cid=<分P cid>     fnval=4048     try_look=1
  wts=<时间戳>        w_rid=<md5>       dm_img_list=[]  dm_img_str=<base64>
  dm_cover_img_str=<base64>            dm_img_inter={"ds":[],"wh":[..],"of":[..]}
Headers: User-Agent=<桌面 Chrome>   Referer: https://www.bilibili.com/
```

`dm_*` 是 B站前端的**用户指纹参数**（来源：`bili-user-fingerprint.min.js`），
`dm_img_str` / `dm_cover_img_str` 是随机字符串的 base64，`dm_img_inter` 里 wh/of 是
按屏幕尺寸算出来的三个整数。照抄 yt-dlp 的生成方式即可：

```python
rnd = lambda n: random.randint(0, n)
wh = [2*1920 + 2*1080 + 3*rnd(114), 4*1920 - 1080 + rnd(114), rnd(114)]
of = [3*10 + 2*10 + rnd(514), 4*10 - 4*10 + 2*rnd(514), rnd(514)]
"dm_img_inter": json.dumps({"ds": [], "wh": wh, "of": of}, separators=(",", ":"))
```

### 3.3 返回结构

- `data.dash.video[]`：同一清晰度有 3 条轨道（`avc1` / `hvc1` / `av01` 编码），按 `id` 分组，**优先 avc1**（兼容性与 ffmpeg 合并最稳）
- `data.dash.audio[]`：`30216`(66k) / `30232`(100k) / `30280`(182k)，取 bandwidth 最大
- 直链字段 `baseUrl` / `base_url`，备份 `backupUrl` / `backup_url`
- **直链必须带 `Referer: https://www.bilibili.com/`**，否则 CDN 返回 `403`（已实测）
- 直链域名是 PCDN 节点（如 `*.edge.mountaintoys.cn:4483`），时效性短，**解析后要立刻下载，不要缓存**

## 5. 关于 buvid 与 Cookie 的实测澄清

上一轮的说法是"游客身份 + buvid 铸造"，实测后需要修正表述：

| 项 | 实测结论 |
|---|---|
| `x/frontend/finger/spi` | ✅ 可用，返回 `data.b_3` / `data.b_4`，直接当 `buvid3` / `buvid4` |
| buvid 对 playurl 清晰度的影响 | ❌ **无影响**（带与不带结果相同） |
| 访问视频页拿 `buvid3`/`b_nut` | ❌ **不要做**：DC IP 上视频页直接 412，且对清晰度无影响；buvid 走 spi 即可 |
| 真正的清晰度闸门 | **`dm_img_*` 指纹参数 + `try_look=1` 同时存在**（缺任一个都只有 480P） |

| 组合 | 拿到的轨道 |
|---|---|
| 仅 WBI + `fnval=4048` | 480 / 360 |
| WBI + `dm_*` | 480 / 360 |
| WBI + `try_look=1` + 网页 Cookie | 480 / 360 |
| WBI + `dm_*` + `try_look=1`（无 Cookie） | **1080 / 720 / 480 / 360** |
| WBI + `dm_*` + `try_look=1` + 网页 Cookie | **1080 / 720 / 480 / 360** |

## 6. 下载与合并

复用现有下载器的思路，但 B站是 DASH 双流：

1. `analyze()` 里把选中的 `(video_url, audio_url, height, qn)` 一起塞进任务上下文（类似 douyin 的 `_douyin` 标记，这里用 `_bilibili`）
2. `_run_bilibili_download()`：两个线程分别流式下载视频轨/音频轨到临时文件（各自汇报 0~50% 进度），
   然后 `ffmpeg -i v.m4s -i a.m4s -c copy -movflags +faststart out.mp4`
3. **ffmpeg 是硬依赖**：没有它只能拿到无声视频。线上已装（docs/08 第 3 步），本地用户跑 `python run.py` 前确认 `ffmpeg -version` 有输出
4. 下载请求同样要带 `Referer`，否则 403；失败重试一次换 `backup_url`
5. 输出文件名/清理逻辑直接复用现有 `_run_douyin_download` 的写法（30 分钟 TTL 不变）

## 7. 出错处理与决策树

| 现象 | 含义 | 处理 |
|---|---|---|
| HTTP 412 | IP / 网关级风控 | 直接回退 yt-dlp；仍 412 → 报"当前网络被 B站 风控，请稍后或换网络" |
| `code: -352` | 风控校验失败（签名/指纹） | 重建 session（新 buvid + 新 dm 参数）重试一次，最多一次 |
| `code: -404` | 稿件不存在 | 报"视频不存在或已删除" |
| `code: 87008` | 充电专属 | 报"该视频为充电专属，暂不支持" |
| `code: -10403` | 地区限制 | 报"该视频在当前地区不可播放" |
| `code: 0` 但轨道只有 480 | dm/try_look 参数没生效 | 检查参数是否被签名排序/过滤破坏（签名必须包含全部参数） |

### 7.1 上线前必做：30 秒定性探测（决定"写不写"）

**写代码之前**先在目标服务器上跑这三条，看 412 出现在哪一层。这一步能把"自研到底有没有用"
从猜测变成结论——**不要跳过**：

```bash
# ① 网页入口（WAF 层）
curl -s -o /dev/null -w "home=%{http_code}\n" -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/151.0.0.0 Safari/537.36" https://www.bilibili.com/
# ② 普通业务 API（未签名）
curl -s -o /dev/null -w "view=%{http_code}\n" -A "Mozilla/5.0 ... Chrome/151.0.0.0 Safari/537.36" -H "Referer: https://www.bilibili.com/" "https://api.bilibili.com/x/web-interface/view?bvid=BV1heam6TExz"
# ③ 凭据接口
curl -s -o /dev/null -w "spi=%{http_code}\n" -A "Mozilla/5.0 ... Chrome/151.0.0.0 Safari/537.36" https://api.bilibili.com/x/frontend/finger/spi
```

| 探测结果 | 结论 | 该怎么做 |
|---|---|---|
| ① 就 412 | IP 在 WAF 层被整段拦截，**自研通道必死** | 不要写代码；换 IP / 家宽出口 / 代理 |
| ① 通、② 412 | API 层风控，可能有参数级特征 | 值得试自研（有不确定性） |
| ①② 通、只有 playurl 412 | 风控在取流环节 | 自研成功率高，按本文实现 |
| 三条全通（412 只出现在 yt-dlp） | 风控针对 yt-dlp 行为特征 | 自研高概率有效 |

**实测记录（2026-10-20，阿里云香港服务器，root 权限执行）**：

```
阶段 1（三层探测，curl）
  home(首页)=200    view(未签名)=412    spi=200

阶段 2（附录 A 脚本）
  page(视频页)  HTTP 412   ← 页面 HTML 被拦，但不影响后面走 API
  spi           HTTP 200
  view*(未签名) HTTP 412
  nav           HTTP 200   wbi_key=ea1db124..
  view-wbi      HTTP 200   cid=42854319052
  playurl       HTTP 200   code=0 heights=[1080,720,480,360] audio=[30216,30232,30280]

阶段 3（附录 B，媒体 CDN Range 下载 200KB）
  video 1920x1080 avc1.640032  host=upos-sz-mirrorcosov.bilivideo.com  HTTP 206  got=204800  header=b'ftyp'
  audio mp4a.40.2              host=upos-sz-mirrorcosov.bilivideo.com  HTTP 206  got=204800  header=b'ftyp'
```

**结论：全链路可行。** `header=b'ftyp'` 是 MP4 的 box 头（`....ftyp`），说明拿到的是真媒体数据，
不是防盗链错误页。412 只落在**未签名的内容请求**上（视频页 HTML、`x/web-interface/view`），
一旦带上 WBI 签名 / 正规凭据接口，请求就正常放行。所以：

- 自研通道在 DC IP 上**能拿到 1080P、也能下载**，不需要住宅代理
- `page 412` 不影响实现——通道直接调 API，不需要抓视频页 HTML
- 注意：本服务器被分配的是 `upos-sz-mirrorcosov.bilivideo.com`（深圳源/海外镜像），**实际下载速率待测**

### 7.2 决策树（2026-10-20 实测后修正版）

> 旧判断"①② 412 就别写"是错的——本服务器 ② 就 412，但签名 playurl 通。
> **关键判据不是未签名接口的 412，而是附录 A 里 `playurl` 的结果。**

```
跑附录 A（签名级探测）
   ├─ playurl HTTP 412                → 内容 API 整体被拦，自研无解 → 换出口 IP
   └─ playurl code=0（拿到轨道）       → 再跑附录 B（CDN Range 下载）
         ├─ CDN 403/412/超时          → 取流通、分发被拦 → 换出口 IP 或代理下载
         └─ CDN 206 + ftyp            → 全链路可行 → 写 bilibili.py
                                        → 家宽实测 → 部署 → 线上实测
```

### 7.3 诚实的预期管理

- **抖音类比不成立**：抖音 `iesdouyin` 分享页本来就宽（免 Cookie 可用），B站 412 是风控网关拒绝，
  两者不是同一类问题，不能拿"抖音能自研成功"推断"B站也行"。
- **但本服务器实测确实通了**：412 只打未签名内容请求，签名 `playurl` 给到 1080P。
  真正的原因是 yt-dlp 先抓页面被打断，而自研通道绕过了页面。
- **仍不是银弹**：B站 可以随时把签名请求也纳入风控（加验证码、加 -352 校验、换签名算法）；
  一旦发生，通道会退化，必须有 yt-dlp 回退 + 明确的错误提示。
- **结论**：这条通道值得做，但它解决的是"绕开被拦的页面层"，不是"让 IP 变干净"。

### 7.4 已验证 / 未验证清单（开工前对齐预期）

**已验证（目标服务器实测）**：签名 `view-wbi` 200、签名 `playurl` 200 且含 1080P、CDN 视频/音频 `206 + ftyp`。

**未验证（实施时必须自己测出来）**：

| 项 | 为什么重要 | 怎么测 |
|---|---|---|
| **全量下载速率与稳定性** | Range 只取了 200KB；PCDN/镜像节点可能限速、中途断流 | 下载完整 1080P（108MB 左右）计时，看均速与是否断 |
| **ffmpeg 在服务进程 PATH 里** | 宝塔启动的进程 PATH 可能不同于 SSH 的 root | 在项目日志里打 `ffmpeg -version`，或下载后检查成品有无音轨 |

| **风控收紧** | B站 可能把签名请求也纳入风控（-352） | 上线后观察错误码；保留 yt-dlp 回退 |
| **带宽成本** | 服务器做中转，出站流量 ≈ 视频体积 | 香港轻量峰值带宽有限，多人同时下载会互相挤 |

## 附录 B：媒体 CDN 下载探测（阶段 2，必跑）

playurl 通 ≠ 能下载。B站 的 `baseUrl` 指向 PCDN / MCDN 节点（如 `*.mcdn.bilivideo.cn:8082`、
`*.edge.mountaintoys.cn:4483`），这一步要确认**服务器能真的把字节拉下来**。

在附录 A 脚本末尾追加（复用已有的 `OP` / `UA` / `REF` / `playurl` 结果变量）：

```python
import random
dash = ((r or {}).get("data") or {}).get("dash") or {}
vids = [v for v in (dash.get("video") or []) if v.get("height") == 1080
        and str(v.get("codecs", "")).startswith("avc1")] or (dash.get("video") or [])

for name, tr in (("video", vids[0] if vids else None), ("audio", auds[-1] if auds else None)):
    if not tr:
        print("%-5s 无轨道" % name); continue
    url = tr.get("baseUrl") or tr.get("base_url")

          tr.get("codecs"), url.split("/")[2]))

    try:
        with OP.open(urllib.request.Request(url, headers=h), timeout=30) as resp:
```

| 结果 | 结论 |
|---|---|
| `HTTP 206` + `header=b'ftyp'` | ✅ 全链路通，可以开工 |

| `412` 或超时 | 媒体分发层也被拦 → 只能换出口 IP / 代理下载 |
