# 方案设计 — 极易下（万能视频下载网站）

> 文档版本：v1.0（2026-10-09）
> 配套文档：`01-需求分析.md`、`../README.md`（运行手册）

## 1. 总体架构

```
┌─────────────────┐      ┌──────────────────────┐      ┌─────────────────┐
│  前端 SPA        │      │  FastAPI 后端 (单端口) │      │  外部            │
│  Vue3 + Vite    │─────▶│                      │─────▶│  yt-dlp 引擎     │
│  构建产物由后端   │ /api │  ├─ analyze 解析      │      │  (B站/YouTube/…) │
│  托管为静态文件   │─────▶│  ├─ download 任务     │      ├─────────────────┤
│                 │ 轮询  │  ├─ task 进度         │─────▶│  抖音自研通道     │
└─────────────────┘      │  ├─ file 文件下发     │      │  (ttwid+分享页)  │
                         │  └─ pay 支付          │      ├─────────────────┤
                         │  任务表=内存字典        │      │  ffmpeg(可选)    │
                         │  文件=downloads/ 临时  │      └─────────────────┘
                         └──────────────────────┘
```

- **单服务单端口**（默认 8000，支持 `PORT` 环境变量），前端构建产物输出到 `backend/static` 由 FastAPI 托管 → 部署形态最简
- **无数据库**：下载任务 = 内存字典 + 锁；文件 = `downloads/` 临时目录，30 分钟 TTL 后台协程清理
- **平台分流**：请求进入后按 URL 判定——抖音走自研通道，其余交给 yt-dlp

## 2. 技术选型及理由

| 层 | 选型 | 为什么 |
|----|------|--------|
| 后端 | Python FastAPI | yt-dlp 本身是 Python 库，**库直调**而非命令行封装：能拿进度回调、异常类型化、零跨语言开销 |
| 下载引擎 | yt-dlp（锁版本） | 1000+ 平台支持由社区维护，我们不承担平台适配风险 |
| 前端 | Vue 3 + Vite（需求方指定） | 构建后是纯静态文件，部署不增加复杂度 |
| 数据库 | 无（内存 + 文件系统） | 需求明确"先不要数据库"；任务生命周期短（30 分钟），内存足够 |
| 支付 | 抽象层 + MockProvider | 见 §5 |
| 合流 | ffmpeg（可选依赖） | DASH 流合并 / 音频提取；缺失时自动降级（仅渐进式格式、禁音频） |

## 3. 核心流程设计

### 3.1 解析 → 下载时序

```
用户                前端                后端                引擎
 │ 粘贴链接/口令      │                   │                   │
 │──────────────────▶│ POST /api/analyze │                   │
 │                   │──────────────────▶│ 平台分流           │
 │                   │                   │──────────────────▶│ extract_info(download=False)
 │ 封面+清晰度列表     │◀──────────────────│◀──────────────────│
 │ 选清晰度，点下载    │                   │                   │
 │                   │ POST /api/download│───创建任务(内存)    │
 │                   │◀─── task_id ──────│───线程池异步执行────▶│ download=True
 │ 进度条             │ GET /api/task/{id}│◀── progress_hook ──│ (每 1.2s 轮询)
 │ 点"保存到本地"      │ GET /api/file/{id}│───FileResponse     │
```

### 3.2 任务状态机

```
downloading ──▶ processing(合并音视频,仅yt-dlp路径) ──▶ done
      └────────────────────────────────────────────────▶ error
done/error 的任务 30 分钟后随文件一起清理
```

### 3.3 兼容性设计细节

- **口令文本**：入口不强制 URL——先用正则从任意文本提取第一个链接（兼容 App 分享口令）
- **清晰度归一**：yt-dlp 返回的原始 format 列表按分辨率分组、每档取最优（mp4 优先），前端只暴露"1080p / 720p / … / 仅音频"这种用户语言
- **音频提取**：yt-dlp 路径用后处理器；抖音路径下载 mp4 后 `ffmpeg -c:a copy` 无损转 m4a

## 4. 抖音免 Cookie 通道（本项目核心自研模块）

### 4.1 为什么不直接用 yt-dlp

yt-dlp 的抖音提取器只会请求 `douyin.com/aweme/v1/web/aweme/detail/`（Web API），
该接口要求**带签名的完整浏览器 Cookie**，且没有降级路径——实测自动铸造的 ttwid /
伪造的 s_v_web_id 均无法通过。主流开源项目（Douyin_TikTok_Download_API）同样
要求手动配置 Cookie，其免 Cookie 版本依赖无头浏览器身份池 + PostgreSQL，过重。

### 4.2 我们的通道（三层递进）

```
① 铸造访客凭证：POST ttwid.bytedance.com/ttwid/union/register/
   （字节官方接口，返回 Set-Cookie ttwid；纯系统自铸，不含任何用户信息，
     进程内存缓存 5 天，失效自动重铸）

② 匿名解析：GET www.iesdouyin.com/share/video/{id}
   （移动端 UA + ttwid Cookie → 返回 SSR 页面，内嵌 window._ROUTER_DATA JSON
     → loaderData["video_(id)/page"].videoInfoRes.item_list[0]
     = 标题/作者/封面/时长/play_addr）

③ 无水印直链：play_addr.url_list 中的 /playwm/ 替换为 /play/
   （HD 档：iesdouyin.com/aweme/v1/play/?video_id={uri}&ratio=1080p&line=0）
```

- **ID 提取**覆盖全部链接形态：`/video/{id}`、`/note/{id}`、任意路径的 `?modal_id={id}`（精选/发现/用户主页）、`v.douyin.com` 短链（读重定向 Location）、口令文本
- **图集/图文**：明确报错"暂不支持"，不静默失败

### 4.3 网络层健壮性（踩坑后的教训）

| 坑 | 现象 | 对策 |
|----|------|------|
| Python urllib 自动读 **Windows 注册表系统代理**；`env -u` 只清环境变量清不掉注册表 | 代理时通时拒 → 间歇性"连接被拒"→ 500 | 模块级 `build_opener(ProxyHandler({}))` **强制直连**（国内站无需代理） |
| 网络偶发抖动 | 偶发失败 | `_get()` 统一封装：重试 2 次 + 递增等待 + 异常转可读 RuntimeError |
| `json.loads` / 字段缺失 | 500 裸错误 | 逐层 try/except → RuntimeError → 接口层兜底 |
| 接口层仍未捕获的异常 | 500 纯文本，前端报 JS 天书 | main.py 兜底 `except Exception` → 400 中文提示 + 服务端日志；前端 `readJson()` 非 JSON 响应转友好提示 |

> **测试方法论教训**：curl 不读系统代理而 Python 读——"curl 测通"≠"代码测通"。
> 网络相关验证必须与实现同技术栈。

## 5. 支付模块设计

```
PaymentProvider（抽象接口）
  ├─ create_payment(order) → 收银台信息（跳转链接/二维码）
  ├─ query_payment(order_id) → 支付状态
  └─ verify_notify(payload) → 校验渠道异步回调签名
       ▲
       │ 实现
MockProvider（当前）：前端弹模拟收银台（伪二维码），
  点击"我已完成支付"→ 后端标记订单 paid → 前端轮询获知
```

- 订单 = 内存字典（与任务表同策略）；定价方案在 `payments.py` 顶部声明
- **接真实渠道（虎皮椒/蓝兔/微信商户号）时只需新增一个 Provider 实现并替换模块级 `provider` 变量**，路由与前端零改动；轮询查单的接口形态与真实渠道的服务器回调等价

## 6. 部署设计

| 环境 | 方式 | 说明 |
|------|------|------|
| 本地开发 | `python run.py`（8000）+ `npm run dev`（5173 代理 /api） | 日常开发 |
| 本地生产 | `npm run build` 后仅 `python run.py` | 单端口全功能 |
| WorkBuddy 发布沙箱 | sites 工具上传 → 沙箱内装依赖 → `PORT` 注入启动 → 反代 HTTPS 子域名 | 当前线上；已实测：抖音✓，B站/YouTube 受云 IP 风控/出口限制 ✗ |
| 自有服务器（升级路径） | 同"本地生产"，代码零改动 | 真正生产级部署 |

**已知部署边界**：发布沙箱仅暴露一个 HTTP 端口、无数据库/Redis——本项目无数据库设计正是为此匹配；若未来需要持久化，选 SQLite。

